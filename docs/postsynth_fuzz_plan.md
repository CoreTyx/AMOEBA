# Fuzzing plan: Cascade on the pin bench

**Status: approved; F0 and F1 done.  Deviations from the plan are logged at the end.**

## Goal

Run large numbers of randomly generated, self-checking programs through
`forte_top`, at three levels:

| Level | Simulator | Purpose | Programs |
|---|---|---|---|
| RTL, 2-state | Verilator, local | Find functional bugs in the core | thousands |
| RTL, 4-state | VCS with xprop, VM | Find X-propagation issues | hundreds |
| Netlist | VCS gate, VM | Show the netlist behaves like the RTL | hundreds |

Every run uses the existing pin bench (`hvl/pin/`): the same agents, checks and
images, and the same `vm_run.sh regress` with cycle-exact RTL-vs-gate trace
comparison. A fuzz program is simply one more image.

## Why Cascade

Cascade (ETH Zurich, USENIX Security 2024; GPL-3.0) builds long programs whose
control flow depends on their data flow. It does this by running each program
once on an ISA simulator, Spike, and using the results to fix up the branches.
A CPU that computes any value wrongly therefore takes a wrong branch and **does
not terminate**. Detecting a bug needs no co-simulation and no internal probes,
only "did the program finish, and are its final registers right?". That is all
a pin-only bench on a netlist can observe, which is why Cascade fits.

The paper reports 37 bugs found across five RISC-V cores, including the RV64
cores CVA6, Rocket and BOOM. It also includes an automatic reducer that shrinks
a failing program to the few instructions that trigger the bug.

## What Cascade needs, and how this chip provides it

Cascade's inputs are the supported ISA extensions, a **stop address**, an
optional register-dump address, and a list of known bugs to avoid. Only the
stop address is used here.

1. **The stop store must reach the pins.** The only off-chip memory is
   cacheable `EXT_MEM`, so the stop store would sit in the write-back D$.
   That's the `tohost` problem again. *Plan:* stop address = `tohost`, and
   patch Cascade's final block to run `fence.i` after the store, exactly as
   every test exit does now. *To verify in F0:* where Cascade emits that block.
2. **Memory never written must read as 0.** Cascade's Spike pre-simulation
   assumes it does, so fuzz images set `mem_policy zero`.
3. **The ISA.** RV64IMAC + Zicsr/Zifencei, M/S/U, PMP, Sv39; no F/D, Zicbo*,
   Svnapot or Svpbmt. Custom state stays out (CSR `0x7c1`, FI_CONTROL, DFT
   lock). *To verify in F0:* whether Cascade generates Sv39 page tables. If it
   doesn't, Linux remains the Sv39 coverage.

**No register dump.** By construction a wrong value means a wrong branch and
no termination, so "finished" is the check. Adding a dump would mean a new
bench command and a second address. Add it only if a bug turns up that ends
cleanly with wrong registers.

## A fuzz image

Generated by Cascade, converted by the existing `generate_memory_file.py`
(it already takes ELFs), and run like every other image:

```
mem_policy zero
load_lst $MEM
reset 16
run_until_tohost <timeout>    # non-termination -> timeout FAIL
expect_tohost 0
finish
```

`vm_run.sh regress` needs no changes: fuzz images get the same `rtl=` /
`gate=` / `trace=` columns as every other image.

## Phases

**F0. Spike-out (local, about one session).** Clone Cascade at a pinned commit
into a gitignored `third_party/cascade` (it's GPL-3.0; a test tool, never in
silicon). Generate programs for the forte ISA, patch the final block, and
answer the two "to verify" items.
- *Gate:* a Cascade program passes the pin bench under Verilator.

**F1. Integration (local).** Replace the `bin/pin_fuzz.py` stub with
`gen N` (programs → `.lst` + `.cmd` in `sim/pin/fuzz/`) and `run` (drives
`pin.sh` serially, so the shared memory image is never contended).
- *Gate:* a scratch RTL copy with one planted bug (for example, a wrong `sltu`
  result for one rare operand pattern) fails within N programs, and the clean
  RTL passes the same N. This proves the loop finds bugs.

**F2. Local campaign (Verilator, RTL).** Thousands of programs, run serially
(at a few seconds each, about 5,000 overnight). Each failure is reproduced
from its seed and run through the existing Spike co-sim flow (`sim/`,
`DUT=forte`), which names the first wrong instruction.

**F3. VM (VCS RTL 4-state and netlist).** `vm_pack.sh` bundles the first N
fuzz images. Random seeds are already diverse, so no selection step. They
run with `ONLY='^fz_' vm_run.sh regress`. At about 1,000 cycles/s on the
netlist, a 2-hour session holds roughly 100–300 programs.
- *Gate:* all of them give `rtl=PASS gate=PASS trace=MATCH`.

**F4. Report.** Programs and cycles per level, bugs found, and what the fuzzer
can't reach.

### Deferred until needed

- **Cascade's program reducer.** Wire it up when the first failure is too long
  to read.
- **Parallel local runs.** Add them if serial F2 is too slow; they need a
  per-program memory image instead of the shared one.
- **A register-dump check.** See above.

## Outside the scope of this plan

- **Asynchronous interrupts.** As far as we know, Cascade drives exceptions
  and privilege changes, not interrupts. `irq` and the timer are covered by the
  directed `irq` test and FreeRTOS. An optional extension: the bench raises
  `irq` at random times during fuzz runs, with Cascade's trap handler taught
  to return. Only if wanted.
- **Fault injection and DFT.** Fuzzing runs with `fault_inject=0`. DFT is
  still a stub.
- **Post-PnR timing.** The same images rerun with an SDF once one exists.

## Decisions needed

1. **Feature scope.** Are S/U modes and PMP in, and Sv39 if Cascade supports
   it? Proposed: everything the core implements except the custom CSR/MMIO
   state.
2. **Budgets.** Local campaign size (proposed: 5,000 programs, or overnight)
   and VM sessions for F3 (proposed: one 2-hour gate session per round).
3. **Bugs found in the core:** fix them on this branch, with a regression
   test each as for the UART, or report them and work around them with
   Cascade's known-bug list?

## Implementation log: findings and deviations

**F0 (spike-out): done.** Cascade at `c3de482` (fetched by
`hvl/pin/fuzz/get_cascade.sh`), driven by `bin/pin_fuzz.py`. Four generated
programs (494–3,687 instructions, 20k–41k cycles) pass on the pin bench
(Verilator, rtl). A program with one executed `jalr`'s address register
changed times out, as it should.

1. **Stop address: the final block is replaced, not patched.** Cascade asserts
   the stop and dump addresses are below `0x8000_0000` (`finalblock.py`).
   Nothing that low is off-chip on this chip, and the UART takes only byte
   stores, not Cascade's `sd`. The driver substitutes its own final block:
   `tohost = 1`, then `fence.i`, then loop. *Planned:* add `fence.i` to
   Cascade's block.
2. **Design profiling is replaced by a constant.** Before generating,
   Cascade runs a program on the design's own simulator to learn which
   `medeleg` bits are writable. The RTL fixes the answer (`csrm.sv`:
   `0xB3FE` with C), so the driver sets it. A wrong value could only cause
   failures, not hide a bug. *Not in the plan.*
3. **No Zicntr/Zihpm on this core**, but Cascade assumes them. Its initial
   block resets `mcycle` and `minstret`, which are illegal here, so every
   program trapped into a loop after four fetches. Its random M-mode CSR ops
   can also pick `minstret`, `mhpmcounter3` and `mhpmevent31`. The driver
   rewrites the resets as `mscratch` writes (same size, same place) and
   removes those three from the random choices. *Not in the plan.*
4. **Cascade generates no page tables.** `satp` and Sv39 appear only in its
   config helpers. The fuzzer covers M/S/U and PMP, but not Sv39, which stays
   covered by the Linux tier. *As the plan's fallback said.*
5. **Seeds:** Cascade's `gen_many_elfs` always seeds 0. The driver has its
   own loop with `--seed`.
6. **Images:** `bin/generate_memory_file.py` rejects Cascade's ELFs (section
   size not a multiple of 8), so the driver writes the `.lst` itself, using
   `objcopy` plus 64-bit words. Side effect: there's no shared
   `sim/bin/memory_8.lst`, so fuzz runs can go in parallel.
7. **What Cascade detects:** a corruption only shows if the bad value
   reaches the control flow. In F0, changing an executed `and` whose result
   is never used went undetected; changing a `jalr`'s address register was
   caught. This is inherent to the method. F1's planted-bug gate measures
   how often a real logic bug surfaces.

**F1 (integration, planted-bug gate): done.** `gen` and `run` landed with F0.
Gate: 20 programs (seed 2) pass 20/20 on the clean RTL. With a planted ALU
bug -- `xor` bit 0 flipped when operand A's low byte is `0x5A`, about 1 in
256 xors -- 1 of the same 20 never terminates (`fz_2_6`), and it passes again
once the RTL is restored. So a rare single-instruction data bug surfaces in
about 5% of programs: enough for a campaign of thousands to catch bugs of
that rarity, too few for a handful. The bug was planted by hand and reverted;
there is no planted-bug script (deferred until it's needed again).
